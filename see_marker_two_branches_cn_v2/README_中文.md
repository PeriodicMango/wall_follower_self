# SeeMarker 两分支现场测试包（修订版）

## 这次最重要的修订

你提出的判断是对的：

> 如果 2.x 的新几何模型本身已经用 angle 对斜视角进行了补偿，
> 那么再强制 Marker 必须接近正对，会削弱这个模型的意义，
> 还可能因为机器人一次都没有正对 Marker 而完全收不到有效点。

所以本修订版做了明确区分：

- **1.x 分支：保留原几何。**
  这里“接近正对过滤”仍然有意义，因为我们的假设正是：
  原几何可能只在接近正对时比较准。

- **2.x 分支：新几何已经考虑 angle。**
  不再要求 Marker 接近正对。
  只过滤极端画面边缘、严重转弯等低质量情况。

---

# 一、1.x：原几何分支

原公式：

```python
x = distance * cos(angle)
y = distance * sin(angle)
```

## 1_原始保底版
完全不加新过滤，现场随时回退。

## 1.1_原几何_只保留接近正对帧
只允许：

```text
|angle| <= 12°
```

用途：
验证“原几何在正对 Marker 的那一段其实是准的”这个猜测。

调参：
- 8°：很严格
- 12°：推荐
- 15°：宽松
- 18°：很宽松

## 1.2_原几何_严格转弯过滤
不限制观察角度，只过滤快速转弯。

默认：
```text
|angular_z| <= 0.20 rad/s
连续稳定 3 帧
```

## 1.3_原几何_正对过滤_加严格转弯过滤
同时要求：
```text
|angle| <= 12°
|angular_z| <= 0.20 rad/s
连续稳定 3 帧
```

最保守，最容易漏 Marker。

## 1.4_原几何_宽松正对_加自适应防漏
为了降低漏 Marker 风险，把正对范围放宽到：

```text
|angle| <= 18°
```

同时使用自适应 Motion Gate。

# 二、2.x：新几何分支

新公式：

```python
x = distance
y = distance * tan(angle)
```

核心假设：

> 图像高度拟合出来的 distance 更接近相机前向深度 x。
> 斜视角的横向位置由 `tan(angle)` 显式恢复。

因此：

> **2.x 不再要求 Marker 必须正对。**

这也是本次修订和上一版最大的区别。

---

## 2_新几何_不限制正对

只改几何函数：

```python
x = distance
y = distance * tan(angle)
```

不加额外过滤。

这是最纯粹的新几何验证版。

---

## 2.1_新几何_只过滤画面边缘

不限制 angle。

只排除靠近图像最左/最右边缘的观测：

```python
EDGE_MARGIN_RATIO = 0.08
```

640 像素宽时，大约是左右各 51 px。

原因不是“斜视角不好”，而是：

- 靠边时 Marker 可能被裁切；
- blob 高度/宽度可能失真；
- 中心点可能偏移；
- 镜头边缘畸变也更明显。

推荐：
- 0.05：宽松
- 0.08：推荐
- 0.10：更保守
- 0.12：较严格

---

## 2.2_新几何_严格转弯过滤

新几何 + Motion Gate：

```text
|angular_z| <= 0.20 rad/s
连续稳定 3 帧
```

但 **完全不限制 Marker 是否正对**。

所以 Marker 在左前方、右前方，只要机器人没有快速转动，都可以参与 mapping。

---

## 2.3_新几何_边缘过滤_加严格转弯过滤

这是我认为 2.x 里最干净的版本：

```text
新几何
+
不靠画面边缘
+
不处于明显转弯
```

没有：
```text
|angle| <= 12°
```

这种“必须正对”的限制。

---

## 2.4_新几何_边缘过滤_加自适应防漏

这是 2.x 的风险规避版。

不要求正对。

规则：

### 正常情况
```text
|angular_z| <= 0.25 rad/s
```
直接允许。

### 中等转弯
```text
0.25 < |angular_z| <= 0.45
```

如果：
```text
Marker 不靠画面边缘
0.75 <= height_ratio <= 1.25
```

仍然允许。

### 快速转弯
```text
|angular_z| > 0.45
```

一律跳过。

所以它不会因为“Marker 从来没正对”而完全丢失。

# 三、你刚才的观点为什么更合理

如果新模型成立：

```python
x = distance
y = distance * tan(angle)
```

那么 angle 本身就是模型输入。

例如 Marker 在左前方 20°：

```text
angle = +20°
```

模型就是用：

```text
y = x * tan(20°)
```

来恢复横向距离。

如果这时我们又说：

```text
只有 |angle| <= 12° 才允许
```

实际上相当于：

> “我设计了一个可以处理斜视角的模型，
> 但又把大部分斜视角观测删掉。”

逻辑上确实矛盾。

所以现在 2.x 已经全部去掉“必须接近正对”的要求。

---

# 四、为什么 2.x 仍然保留边缘过滤

这不是因为模型不能处理角度。

而是因为：
- Marker 贴到图像边缘时可能只剩半根；
- 此时 `h`、`cx` 都可能不是真实值；
- 任何几何模型拿到错误输入都会错。

所以我们区分：

```text
中等斜视角
→ 可以保留

几乎出画面的极端边缘
→ 质量差，过滤
```

这比“只保留正对”更合理。

# 七、现场最重要的判断

如果你们在新几何下看到：

```text
Marker 在左前方
机器人还没转
Marker 在 RViz 里基本固定
```

这是非常好的信号。

如果：

```text
Marker 随 angle 改变仍然系统性前后跑
```

说明：
- 新 geometry hypothesis 可能不对；
- 或 angle/FOV 本身也需要校准。

如果：

```text
直行时稳定
一开始转弯就跑
```

说明：
- geometry 可能已经解决；
- motion/timing 才是剩下的问题。
